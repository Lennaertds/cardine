## Goal

A fourth Zed server, **DeepSeek Harness (cardine)**, that lets an agent from another
project (today: `Bachelorproef_2027_Codebase_Indexing`) see the essential part of Cardine
as it really is — architecture, ADRs, product docs, the lab — and nothing else. The
agent reads Cardine to *ask about it*. It cannot change it, cannot run anything in
it, and never sees what is deliberately left out.

## Scope

- **In:**
  - A fourth profile `cardine`, generated by
    `install-lab.sh --profile cardine --mode cardine --roots <git-roots…>`.
    The profile still lands in `~/.dsh/profiles/cardine/cordis.patch.yml`, so
    `dsh --profile cardine` and the Zed server **DeepSeek Harness (cardine)**
    follow the existing naming (install-lab 0.5.3). No second copy of the installer.
  - **Roots, not one root.** Cardine is the outer folder (`Cardine/`) with `cardine/`
    (this repo) and `Bachelorproef_2027_Codebase_Indexing/` inside it —
    [install-lab.sh](../../../packages/lab/install-lab.sh) itself treats them as two
    separate profiles. This profile names the `cardine/` root; more roots are
    deliberately later.
  - **A visible set per root** (the table below). Not "all of Cardine".
  - **Read-only and no shell.** In v1 `tool-shell` is off and the shell path is not
    built at all: no `cardine-bwrap` mode, no second argv parser. What the agent
    needs to look lives in `read`/`glob`/`grep` and in the index. A read-only shell
    is deliberately later, with its own proof.
  - **A scope guard** (`cardine-scope-guard`, a new plugin next to
    `cardine-secrets-guard/`) on `tools/pre-execute`. It refuses, for
    `read`/`read_image`/`glob`/`grep`/`list` (and `write`/`edit` if a later profile
    mounts them), any path outside the visible set. Deny-only, `realpath` plus the
    parent walk for not-yet-existing paths: `..`, symlinks and relative paths cannot
    escape.
  - `approval: never`; `tool-web`/`tool-todo`/`tool-goal` off (the DeepInfra
    `triggers` error, lab CHANGELOG 0.3.0); `sandbox-policy: workspace-write` on the
    root as DSH's fallback; `tool-fs`: read/read_image on, write/edit/applyPatch off.
  - **No slice check.** Today's `cardine-slice-check` runs `make check` — an
    execution in Cardine. This profile inserts none.
  - `cardine-status.sh` reports the profile, its mode and its roots.
- **Out of scope:**
  - Any edit of Cardine by this agent — not even a proposal file. An external agent
    that reads Cardine is a reader; proposals go through the human or the BP repo.
  - The reverse direction (a Cardine agent seeing the BP repo): the BP agent already
    has that root in its own `bp` profile.
  - **`bron/` and `kit/`.** They are excluded not for size (that cannot be checked
    from inside a session) but for meaning: `kit/` is a template, not house rules
    ([cardine/AGENTS.md](../../../AGENTS.md)), and `bron/` is the Dutch working
    source. Also out: `data/`, `.git/`, `node_modules/`, `__pycache__/`, `.env*`,
    `scripts/`. The table below is exclusive: anything not named does not exist.
  - Indexing from the session (`mcp__jarvis__indexRepo` stays banned,
    [ADR 0014](../../decisions/0014-index-repos-separately-and-run-install-lab-for-new-projects.md)).
  - Running Cardine's `make` targets, tests or dev server anywhere.
  - macOS/Windows: Linux only, like the rest of the lab.

## Visible set — what the profile may see

Per root, one table in `install-lab.sh` (single source, the way the lab profile is).
For `cardine/`:

| Root | Visible | Excluded (does not exist in the session) |
|------|---------|-------------------------------------------|
| `cardine/` | `README.md`, `AGENTS.md`, `docs/**`, `standard/**`, `sjablonen/**`, `new-project/**`, `existing-project/**`, `packages/lab/**`, `Makefile`, `package.json`, `CHANGELOG.md`, `LICENSE`, `LANGUAGE-MIGRATION.md`, `BOOTSTRAP.md` | `bron/**` (sources, PDFs, Dutch notes), `kit/**` (a template, not rules), `data/**`, `.git/**`, `node_modules/**`, `**/__pycache__/**`, `scripts/**` (optional tools, not architecture), `.env*` |

`docs/**` is the ADRs and product docs — the "most important part" the agent asks
about. `packages/lab/**` is in because it *is* the system level: the bwrap cage, the
guard, the installer. Excluded paths are refused by the guard with a named reason,
and absent from the index (Risk 1).

## System level — what "see" means here

Three pieces, and the first is the one that does the work:

| Piece | Who enforces | What it covers |
|-------|--------------|----------------|
| Tool guard | `cardine-scope-guard` on `tools/pre-execute` | `read`, `read_image`, `glob`, `grep`, `list` run in the DSH host process (`dsh-fs-local`: cwd is not a boundary). The guard resolves every path with `realpath` (+ parent walk) and refuses anything outside the visible set. `prepend: true`, so it runs before every other listener. |
| Profile | `cordis.patch.yml` | `tool-shell` disabled; `tool-fs` read/read_image on, write/edit/applyPatch off; `approval: never`; `sandbox-policy: workspace-write` on the root; no web/todo/goal; no slice check. |
| Index (MCP) | `mcp-jarvis` | Read tools only, from Cardine's own index (Risk 1: that index holds `bron/` today, so it needs a scoped build). |

The shell is off, so the mount layer of the lab (`cardine-bwrap`) does not appear
here. That is the strongest version of "only that": it also removes the whole class
of cage problems the lab had (nested `bwrap`, `/tmp`, a second argv parser). The
system view the agent gets is the *source tree as the system uses it* — profile,
plugins, docs, decisions — not a machine to poke at.

## Interfaces

- Modules and files: `packages/lab/install-lab.sh` (`--mode cardine`, `--roots`, the
  visible-set table), `packages/lab/cardine-scope-guard/` (new: `index.js`,
  `index.test.js`), `packages/lab/scripts/check-sandbox.sh` (a profile-source check
  for `--mode cardine`), `packages/lab/cardine-status.sh` (report the profile).
- Interface that changes: `install-lab.sh --profile NAME [--name LABEL] [--mode lab|cardine] [--roots PATH…]`
- Seams touched: harness → fs tools (the plugin), harness → indexing (MCP). The
  harness → shell seam is deliberately not built.
- Example to follow: `packages/lab/cardine-secrets-guard/` (deny-only, `realpath`,
  `prepend: true`, `node --test`) and the `--profile` handling in `install-lab.sh` (0.5.3).

## Slices (each testable on its own, one session, through the whole stack)

1. **Profile skeleton.** `install-lab.sh --mode cardine --roots <cardine>` writes a
   profile with the lab exclusions (shell off, writes off, never, no web/todo/goal,
   no slice check). `dsh --profile cardine --dump-config` shows it; a second run
   changes nothing.
2. **Scope guard + visible set.** `cardine-scope-guard` with the table, one root.
   Tests: `read cardine/docs/product/harness.md` passes;
   `read cardine/bron/bronnen.md`, `read cardine/kit/kern/AGENTS.md`,
   `read <root>/docs/../bron/bronnen.md`, `read ~/.dsh/.env` and a `glob` above the
   visible set are refused with a named reason; a symlink inside the set that points
   at `bron/` is refused.
3. **Scoped index.** Build Cardine's index for this profile over the visible set only
   (a `jarvis` run with the exclusion list, output under `data/runtime/`, or a scoped
   copy); `mcp__jarvis__searchCode "uithangbord"` must return no `bron/` hit.
4. **A real BP thread.** In Zed: a BP window, **DeepSeek Harness (cardine)**, run the
   scope prompt in `docs/architecture/test_prompt.md` and keep the hit list.

## Acceptance

- [ ] `install-lab.sh --profile cardine --mode cardine --roots <cardine>` from the BP repo writes a profile whose `workspaceRoot` and jarvis `cwd` point at Cardine; a second run changes nothing (idempotent).
- [ ] `bash packages/lab/scripts/check-sandbox.sh --profile cardine` is green: guard matrix (inside passes; outside, excluded, `..` and a symlink all refused with a named reason) and profile matrix (`tool-shell` absent, write/edit/applyPatch off, `approval: never`).
- [ ] In a fresh BP thread on `DeepSeek Harness (cardine)`: `read <root>/docs/product/totaalproduct.md` passes; `read <root>/bron/bronnen.md`, `read <root>/kit/kern/AGENTS.md` and `read ~/.dsh/.env` are refused **with a clear reason**, not a raw EACCES and not "unknown tool" that reads as a bug.
- [ ] `mcp__jarvis__searchCode` on this profile returns nothing from `bron/` or `kit/`.
- [ ] The lab profile (`acp`) and the BP profile (`bp`) are unchanged: an empty diff against their `cordis.patch.yml`, and `make sandbox-check` stays green.
- [ ] `make links` and `make check` green; `packages/lab/CHANGELOG.md` gets a 0.6.0 entry.

## Risks / open

1. **The index is not the guard.** `jarvis index` on `cardine/` today also indexes
   `bron/` ([ADR 0014](../../decisions/0014-index-repos-separately-and-run-install-lab-for-new-projects.md)),
   so a search would show what the guard hides from `read`. Slice 3 builds a scoped
   index; accepting the leak instead is a decision for the user, not the default.
2. **MCP results are not path arguments.** The guard sees tool *parameters*, not
   returned text, so it cannot filter MCP hits. That is why Risk 1 must be solved at
   index time.
3. **The shell is off now, not forever.** A later read-only shell must reuse
   `cardine-bwrap` with a mode flag (not a second policy), run under `--unshare-net`
   and be proven in `check-bwrap-secrets.sh` in both modes; without that, do not build it.
4. **A profile is not per-agent.** The Zed server is global: anyone who picks
   **DeepSeek Harness (cardine)** for a Cardine window gets this narrow view. The
   server name says what it is, and that is accepted.

## Deliberately later

| Extension | Why later | Ask when |
|-----------|-----------|----------|
| A ro shell (`bwrap --cardine`, `--unshare-net`, visible set only) | Reading is enough without one; a shell is the biggest surface | A BP question needs `git`, `make -n` or a tree listing that `glob` cannot give |
| A second root (the BP repo beside Cardine as reference) | One root proves the shape; the BP agent already has its own | A BP task cites Cardine and BP files together |
| A native read-only sandbox from upstream DSH | Only if upstream offers one with the same proof | The DSH changelog mentions it |
