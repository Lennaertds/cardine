## Went wrong

- **`digest-place` wrote 263 sections into the wrong themes.** Insertion looped in theme order while mutating the line list; every insert shifted all later spans, so all of §197–§274 landed in Prompt Engineering. Fixed by inserting **bottom-up** plus a guard that refuses to write if any § would fall outside a theme. **Lesson: never mutate a list while iterating positions computed from its old length.**

- I reported files as restored when they were not, three times. `git checkout -- …` goes through a wrapper that does not restore, and `/tmp` is not writable here, so an `cp` to `/tmp` silently failed. Each time my next measurement (`grep -c '^## §'`) said 196 and I read that as success — for one of the runs the count was 196 because it *duplicated* the check, not because the file was clean. **Lesson: prove a restore with `git status --short` (empty = identical to HEAD), not with a count that two different states can share.**

- Two of my own shell edits were broken and I only noticed because a validation step caught them: a `(S:=None,None) if False else …` artefact and a stray `141b:=None,` in a hand-written dict. Large literal tables should be **generated and validated** (length, key set) before use, which is what finally worked.

- The keyword theme router agrees with my own 263 decisions only **45%** of the time (66% precision when it commits). It is a pre-sorter, not a classifier; the honest fix was to make it answer `uncertain` more often instead of guessing. Measured, not assumed.

- `papers/search?q=…` on HF is **relevance-ranked over 2017→now**, not date-sorted, so with the default `DIGEST_JSON_DAYS=90` a 120-result query keeps 0–3 items. Broad queries also match company names (`q=sandbox` → "SandboxAQ"). Narrowed to `sandbox coding agent` / `computer use agent` and documented it in `SOURCES.md`.
- The English language guard never saw most of the leakage fixed above: it only scans `.md/.sh/.js/.py/.yml/.yaml/.mk/.toml`, so `.mdc`, `.alloy`, `.env.example`, `.c`, `.h` and `.rs` were never checked. A package scan (pack the tarball, walk every shipped file) is what found it. Consider extending `check-language.sh`'s `exts` to those suffixes, or to everything not binary.

- The second cause is `.gitignore` vs `npm pack`: `local.mk` is gitignored and untracked, but `npm publish` filters on `files`, not on git. Anything gitignored inside a published directory ships. `sync_kit.sh` uses `rsync -a` without `--delete`, so files deleted from source `kit/` keep living in the distribution copy. `--delete` (or `--delete` plus an exclusion list) would make the two copies provably equal.

- `npx cardine` was the documented route for a command that has durable state (`status`, `--fix`, `version`). npx re-downloads per invocation and gives no stable binary; the lab already used a global install, so the root README and the package disagreed. One route, global npm, now.

- Two bad calls in a row on the `cardine-lab@0.5.3` publish. I read the "being processed" notice as a *staged* publish and told the user nothing had landed; then, when `dist-tags` showed 0.5.3 while the tarball URL still returned 404, I called it a broken half-publish (metadata without blob) and recommended `npm unpublish`. It was neither: the metadata goes live first and the tarball CDN is lazy per edge, so a consistent 404 for several minutes meant "not cached here yet". The publish was correct the first time. **Lesson: after `npm publish`, verify with a real `npm i -g <pkg>@<version>`, and on a 404 wait and retry — never unpublish on the strength of a tarball 404 alone.** An unpublish would have cost the user the 72h window for no reason.

- An assertion aborted a script *after* it had already copied a stale file into `docs/packages/`: `cp` ran unconditionally before the guarded edit, so the mirror briefly held a half-edited copy. Edits on mirrored pairs are safer as one Python step that writes both, then `diff -q`, rather than `edit` → `cp`.

- Shell parse errors, not code errors, cost two round-trips: a heredoc containing a stray quote, and a `cd a; cd b` chain where a `fatal:` from a wrong-directory `git add` did not stop the following `git commit` — it committed only the pre-staged rename and produced a commit whose message described the whole slice. Use `&&` between dependent commands. The user also hit `zsh: number expected` from `...` inside a `#` comment following a command; and a `commit` pasted from a shell persisted as a multi-line subject. Comments belong on their own line.

- A tag was created before it was verified: `git tag v1.0.0` ran when it already existed (pointing at the earlier, empty commit `75e658d`, where the package was still `@lennaertds/cardine-structure@0.5.1`). Had it been pushed, CI would have published the old package. Deleting and re-tagging on the right commit is only safe because it was unpushed. **Check `git tag -l` and what a tag contains (`git show <tag>:packages/structure/package.json`) before pushing, not after.**
